The Fast Way (Recommended)

One script checks everything below.

  1. Download the workshop package. Go to the releases page and take the newest sko27-japac-idira-ai-workshop.zip. That is the file you want, not “Source code (zip)”.
  2. Extract it into your Downloads folder. Double-click it on macOS; right-click and choose Extract All on Windows. You should end up with Downloads/sko27-japac-idira-ai-workshop.
  3. Open a terminal, go to that folder, and run the script.

    Press ⌘ + Space, type Terminal, press Return. Then:

    cd ~/Downloads/sko27-japac-idira-ai-workshop
bash check-prereqs.sh

    Press the Windows key, type PowerShell, press Enter, not Command Prompt. Then:

    cd $HOME\Downloads\sko27-japac-idira-ai-workshop
Get-ChildItem -Recurse | Unblock-File
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
.\check-prereqs.ps1

    🛑 About the two middle lines. Windows marks every file that came out of a downloaded zip as untrusted. Unblock-File clears that mark on this folder, so you are not asked to approve each script. Set-ExecutionPolicy allows scripts in this window only. Neither one needs admin rights.

    🛑 Asked to approve the script anyway? You skipped the Unblock-File line. Answer R to run it once, or run that line and start again.

Every offer is a [y/N] question. Answer n and it changes nothing. It offers to rehearse step 7, your AWS access, for real: say yes to that one.

One offer sets Claude Code to auto mode by default. In auto mode the agent runs commands without asking you first, and the afternoon lessons assume it. Say yes. It applies to every folder on this laptop, not only the workshop one, and Lesson 07 shows you how to undo it.

Two extra options:

  • Just look, change nothing: bash check-prereqs.sh --check-only .\check-prereqs.ps1 -CheckOnly
  • Say yes to everything: bash check-prereqs.sh --yes .\check-prereqs.ps1 -Yes

🛑 Does idsec say “is not recognized”? A PowerShell window keeps the PATH it started with. The script puts idsec on your PATH. A window opened before that does not have it. Close every PowerShell window, open one, then check it:

It prints a version number. Still not recognized? Load the saved PATH into the window you are in:

$env:Path = [Environment]::GetEnvironmentVariable('Path','Machine') + ';' + [Environment]::GetEnvironmentVariable('Path','User')

Nothing prints. Run idsec version again and it works. The same fix applies to claude and jq.

3

Make a virtual environment

A virtual environment is a private folder holding this project's Python libraries. Three reasons it matters to you today:

  • Nothing is installed system-wide, so nothing needs admin rights.
  • The workshop cannot break some other tool on your laptop that also uses Python.
  • Cleaning up afterwards is deleting one folder.

From inside the sko27-japac-idira-ai-workshop folder, create it:

python3 -m venv .venv

If step 2 showed that your machine calls it python, use that word instead.

Then activate it:

source .venv/bin/activate
py -m venv .venv

If step 2 showed that your machine calls it python, use that word instead.

Then activate it:

.\.venv\Scripts\Activate.ps1

🛑 “running scripts is disabled on this system”? Common on managed Windows laptops, and no admin rights needed to work around it. This allows scripts for this window only, then activates:

Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
.\.venv\Scripts\Activate.ps1

If you would rather not repeat that in every window, -Scope CurrentUser -ExecutionPolicy RemoteSigned makes it stick for your account only.

Your prompt now starts with (.venv). That is how you know it is on.

Install what the two apps need, the sandbox app you fix in Part 2 and the harness lessons you build in Part 1:

pip install -r sandbox-app/requirements.txt
pip install -r ai-harness-app/requirements.txt

And check them both:

python -c "import boto3, anthropic, rich; print('libraries ready')"

It prints libraries ready. No library needs admin rights, and they all land inside .venv.

📌 The one thing to remember from this page. A virtual environment is per terminal window. Open a new window and the (.venv) is gone, and Python will not find boto3. The fix is always the same. cd to the workshop folder and activate again:

cd ~/Downloads/sko27-japac-idira-ai-workshop
source .venv/bin/activate
cd $HOME\Downloads\sko27-japac-idira-ai-workshop
.\.venv\Scripts\Activate.ps1

This is the single most common problem on the day. It is also the easiest to fix.

⚠️ Still command not found in a new window? The installer puts claude in ~/.local/bin and is supposed to add that folder to your PATH. Sometimes it does not. Check the file is there:

ls ~/.local/bin/claude

If it prints the path, add the folder yourself:

echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.zshrc
Get-Item $HOME\.local\bin\claude.exe

If it prints the path, add the folder to your own PATH:

$user = [Environment]::GetEnvironmentVariable("Path", "User")
[Environment]::SetEnvironmentVariable("Path", "$user;$HOME\.local\bin", "User")

Then open a new window and run claude --version again. The setup script offers this same fix.

5

Install the idsec CLI and jq

Two command-line tools. idsec is Idira's, and jq reads the answers it gives back. Both are a single file, with no installer.

idsec

Download the archive for your machine from the official releases page:

github.com/cyberark/idsec-cli-golang/releases

Take the newest release and pick the file matching your machine:

MachineLook for a file name containing
Mac with Apple silicon (M1–M4)darwin and arm64
Mac with an Intel chipdarwin and amd64
Windowswindows and amd64

Not sure which Mac you have?

uname -m

arm64 means Apple silicon. x86_64 means Intel.

Switch this page to macOS if you are on a Mac.

📛 The file inside is not called idsec. The archive names the program after the platform it was built for, so on a Mac you get idsec-darwin and on Windows you get idsec-windows.exe, next to a licence and a readme. Every command in this guide says idsec, so the install below renames it. That rename is the only fiddly part of this step, and it is why the commands look longer than a one-liner.

Make a folder for personal tools, unpack the program into it under the name the guide uses, and tell your shell where to look:

mkdir -p ~/bin
tar -xzf ~/Downloads/idsec_*.tar.gz -C ~/bin idsec-darwin
mv ~/bin/idsec-darwin ~/bin/idsec
chmod +x ~/bin/idsec
echo 'export PATH="$HOME/bin:$PATH"' >> ~/.zshrc

Downloaded more than one archive? Put the exact file name in place of idsec_*.tar.gz.

Close the terminal, open a new one, then check:

idsec version

If macOS refuses to run it (“cannot be opened because the developer cannot be verified”), run this and try again:

xattr -d com.apple.quarantine ~/bin/idsec

Make a folder for personal tools, unpack the program into it under the name the guide uses, and add that folder to your own PATH. That is a user-level setting, so no admin rights are needed:

New-Item -ItemType Directory -Force $HOME\bin | Out-Null
$archive = (Get-ChildItem $HOME\Downloads\idsec_*windows*.tar.gz)[0].FullName
tar -xzf $archive -C $HOME\bin idsec-windows.exe
Move-Item $HOME\bin\idsec-windows.exe $HOME\bin\idsec.exe -Force
$user = [Environment]::GetEnvironmentVariable("Path", "User")
[Environment]::SetEnvironmentVariable("Path", "$user;$HOME\bin", "User")

The second line finds the archive, so you do not type a version number. Then close PowerShell and open a new window, because the PATH change only applies to new windows:

idsec version

If Windows blocks the file, right-click $HOME\bin\idsec.exe → Properties → tick Unblock → OK.

jq

jq reads one value out of a block of JSON. Idira returns your AWS credentials as JSON, so jq is what puts them into your terminal. It goes in the same ~/bin folder, already on your PATH.

mkdir -p ~/bin
curl -fsSL -o ~/bin/jq "https://github.com/jqlang/jq/releases/latest/download/jq-macos-$(uname -m | sed 's/x86_64/amd64/')"
chmod +x ~/bin/jq
xattr -d com.apple.quarantine ~/bin/jq 2>/dev/null; jq --version

You should get something like jq-1.7.1. The second line picks the build for your chip on its own.

New-Item -ItemType Directory -Force $HOME\bin | Out-Null
Invoke-WebRequest -Uri https://github.com/jqlang/jq/releases/latest/download/jq-windows-amd64.exe -OutFile $HOME\bin\jq.exe
jq --version

You should get something like jq-1.7.1. If nothing is found, you are in the window you had open before the PATH change. Open a new one.

If either program refuses to run and the message mentions a policy, an administrator, or Idira Endpoint Privilege Manager, that is application control doing its job. It decides which programs are allowed to run on a managed laptop. Please do not try to work around it. If you are offered a Request authorization button, use it; otherwise ask in #cybr-japac-ts-all today and we will get idsec allowed for you.

6

Set up your idsec profile and log in

You log in with your own CYBRWorld account. This is the CyberArk demo tenant you already use, at demo.cyberark.cloud. Nobody issues you a workshop account.

idsec configure

It asks a few questions. Three of the answers matter:

QuestionAnswer
Identity Tenant Subdomaindemo
Identity URLhttps://aam4614.my.idaptive.app/
Usernameyour own, ending in @cyberarklab.com

Where a question shows a default in brackets, press ReturnEnter to accept it.

🔎 Check what it wrote. Your answers land in one file. Read it back:

cat ~/.idsec/profiles/idsec
Get-Content $HOME\.idsec\profiles\idsec

It should look like this, with your own username:

{
    "profile_name": "idsec",
    "profile_description": "",
    "auth_profiles": {
        "isp": {
            "username": "<your name>@cyberarklab.com",
            "auth_method": "identity",
            "auth_method_settings": {
                "identity_mfa_method": "",
                "identity_mfa_interactive": true,
                "identity_url": "https://aam4614.my.idaptive.app/",
                "identity_tenant_subdomain": "demo"
            }
        }
    }
}

A different identity_url or identity_tenant_subdomain is another tenant, not CYBRWorld. Run idsec configure again with the three answers above.

Then log in:

idsec login

Follow the prompts. Usually the sign-in happens in the terminal: your password, then a multi-factor check. Sometimes a browser window opens instead, so sign in there and come back. Either way you end up with a success message.

🔑 Which password? Your own CYBRWorld password. Nothing is echoed as you type it, which is normal.

👥 Already using idsec for another tenant? Then you already have a default profile, the one called idsec. CYBRWorld has to go there. Every command in this guide leaves --profile-name off, so every command uses that one profile. Keep your old tenant first, under a name of its own.

Copy the folder, so you can put it back afterwards:

cp -R ~/.idsec/profiles ~/idsec-profiles-backup
Copy-Item -Recurse $HOME\.idsec\profiles $HOME\idsec-profiles-backup

Now save the old tenant under its own name. It asks the same questions again, so have that tenant's values to hand:

idsec configure --profile-name <that-tenant>

Then run it with no name, and give it the three CYBRWorld answers above:

idsec configure

That writes the default profile. Check the names with:

idsec profiles list

⚠️ Once only. Do this now and then leave it alone. On the day you will only need idsec login. Running idsec configure again overwrites the default profile, and that is a detour you do not want on the day.

7

Get your AWS credentials, once

A problem here stays invisible until the session starts, so do the whole thing now. You will run these same three commands on the day.

First, see what you are allowed. You must be logged in from step 6:

idsec exec sca cloud-access list-targets --csp aws

You should get at least one AWS account with at least one role next to it.

🚩 An empty list, or an error about policy? Ask in #cybr-japac-ts-all today. This is an entitlement that has to be granted for you, and it cannot be fixed from your seat on the day.

Second, ask for the credentials. One line. Use the Copy button:

eval "$(idsec exec sca cloud-access elevate --csp aws --workspace-id 409556437035 --roleIds arn:aws:iam::409556437035:role/CW-SCA-AdminAccess --raw | jq -r '.response.results[0].accessCredentials | fromjson | "export AWS_ACCESS_KEY_ID=\(.aws_access_key)\nexport AWS_SECRET_ACCESS_KEY=\(.aws_secret_access_key)\nexport AWS_SESSION_TOKEN=\(.aws_session_token)"')"

Nothing prints. That is success.

idsec exec sca cloud-access elevate --csp aws --workspace-id 409556437035 --roleIds arn:aws:iam::409556437035:role/CW-SCA-AdminAccess --raw | jq -r '.response.results[0].accessCredentials | fromjson | [.aws_access_key, .aws_secret_access_key, .aws_session_token] | @tsv' | ForEach-Object { $ak,$sk,$token = $_ -split "`t"; $env:AWS_ACCESS_KEY_ID=$ak; $env:AWS_SECRET_ACCESS_KEY=$sk; $env:AWS_SESSION_TOKEN=$token }

Nothing prints. That is success.

Idira just granted you an AWS role and handed back credentials that expire. jq put them into this terminal window. They were never written to a file, and never shown on screen.

Third, prove it worked. With the virtual environment switched on from step 3:

python -c "import boto3, urllib3; urllib3.disable_warnings(); print(boto3.client('sts', verify=False).get_caller_identity()['Arn'])"

verify=False turns off the TLS certificate check. Some corporate networks inspect traffic, and the check fails on this call. Do not copy that switch into real code.

You should get a long line ending in assumed-role/CW-SCA-AdminAccess/<your-name>. Your own name is in it, which is the part a shared access key could never tell you.

⚠️ One terminal window only. Those three variables live in this window and they expire. That is the point of them, not a fault. On the day you will run this again, and Lesson 09 explains why.

🚩 jq: command not found, or an error about accessCredentials? The first one means step 5 is not finished, or you are in the terminal you had open before the PATH change. The second means the elevation itself failed, so run the command without the | jq part and read what Idira actually said. Ask in #cybr-japac-ts-all today if it is a policy message.

8

Check you can reach AWS

Everything you run today talks to AWS over HTTPS. This confirms there is a route. With the virtual environment switched on:

python -c "import socket,ssl; h='bedrock-runtime.us-east-1.amazonaws.com'; ssl._create_unverified_context().wrap_socket(socket.create_connection((h,443),10),server_hostname=h); print('AWS reachable')"
python -c "import socket,ssl; h='bedrock-runtime.us-east-1.amazonaws.com'; ssl._create_unverified_context().wrap_socket(socket.create_connection((h,443),10),server_hostname=h); print('AWS reachable')"

AWS reachable is the whole answer.

🚩 A timeout or Connection refused instead? There is no route to AWS from this network. The cause is usually a VPN, a firewall, or egress filtering. That does stop both halves of the workshop. Ask in #cybr-japac-ts-all today with what it printed. If you will be on a different network on the day, run this again there: reachability is a property of the network, not of your laptop.

🔍 What about a proxy that inspects HTTPS? Some corporate networks decrypt and re-sign traffic on the way past. That used to end the workshop at lesson 01. It no longer does, because the Part 1 scripts do not check certificates at all. That is a deliberate workshop-only shortcut. It is written up in full at the top of ai-harness-app/config.py. It is not what you would do at a client. The cheat sheet says what to do instead.

The setup script still reports it, under “How this network treats HTTPS”, because it is useful for us to know in advance. It is information, not a blocker.
