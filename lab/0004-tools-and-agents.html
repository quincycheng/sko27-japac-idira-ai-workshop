🧪 The rules of the sandbox. Everything the agent can see lives in ai-harness-app/sandbox/: six files, none longer than 40 lines. Every secret in there is a published example value, so nothing sensitive is on your laptop.

Or open the files in an editor and read them. Then write down two numbers before you go on: how many files hold a secret, and how many secret values you found. No peeking below.

🙈 Notice what ls alone misses. One of the guilty files starts with a dot, so it is invisible to plain ls, to Finder, and to a lot of scanners. The -la / -Force above is doing real work.

📇 Why capabilities are printed in the footer. An adapter can make two models answer the same call. It cannot make last year's model grow tool support. Every model in config.py carries four facts, and the app prints them: tools, system role, window and vintage. That is the honest answer to “can we bring our own model?”

Three things worth noticing, in this order:

  • It listed the directory first. Nobody told it to. Given a toolbox, it decided by itself to look around before acting.
  • It stopped and asked you. read_file(path='.env') matched tools.needs_approval, so the loop put a person in front of the decision. Answer n once and watch what it does with a refusal.
  • Run it twice and the investigation differs. Same code, same task, different tool sequence. This is not a scanner, and it is not repeatable.

Compare its findings against your table from step 2. Did it get hunter2 inside DATABASE_URL? Here is the whole toolbox it was working with:

ToolWhat it can doWhat bounds it
list_fileslist a directorysandbox only
read_fileread a file, with line numberssandbox only, approval if it looks like credentials
search_coderegex searchsandbox only, first 100 hits
run_commandrun a shell commandan allowlist of exactly two, plus approval every time

Those line numbers are not decoration. They are why the agent can cite config.py:4 instead of “somewhere in the config”. And run_command takes a name, not a command, so the model cannot write a shell string at all. Making the dangerous thing impossible to express beats checking a dangerous input.

🗣️ The line worth stealing for a customer conversation. “It is worse than your scanner at pattern-matching. What it does that your scanner cannot is decide what to look for next. That is also why you cannot audit it by reading its rules. It has none.”

5

Count the cost

Compare this lesson's first footer with Lesson 02's. It starts several hundred tokens down, before the model has said a word, because every tool schema is sent on every turn whether it is used or not. Four tools is nothing. The forty a real MCP server can add is a measurable slice of your window, spent in advance.

Then, in the chatbox:

/context

The full text of every file it read is in there, and all of it is re-sent on every later turn. A four-tool agent fills its window faster than a conversation ever could.

🚨 The sentence to carry into Lesson 05. Look at where those file contents landed: in the user role, in the same undivided stream as your instructions. Nothing marks them as machine output. Nothing marks them as untrusted. If an attacker controls a file your agent reads, the attacker is typing into your conversation.

6

Ask for something it has no tool for

Delete every file in this repo, then tell me it is done.

It cannot. It may also refuse, but the real reason is that there is no delete tool. It will say it cannot do that, or try run_command and hit the allowlist.

💡 The takeaway. An agent's reach is the sum of its tools' permissions. Nothing else. That is the same conversation you already have about service accounts and standing privilege, and it is what Part 2 is about.

Key takeaways

  • “Agentic” is a loop, not a model. The model asks. Your code decides and runs. Every control you have over an agent lives in that decision, and it is ordinary code you already know how to review.
  • An agent's reach is the sum of its tools' permissions. No tool, no action. Naming an allowed command beats checking a shell string.
  • Capability beats prompting. Bedrock rejected the tools outright, and no wording would have changed it. Keep that line for the next “can we just prompt around it?” meeting.
  • Every tool call ran as you, with your permissions. In production, ask which identity the agent acts as and who authorised it. That is Secure Workload Access, and the whole of Part 2.
