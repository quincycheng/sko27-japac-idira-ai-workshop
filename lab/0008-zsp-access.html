Part 2 · Lesson 08

Zero standing privileges 🎫

Instead of owning a key forever, you are going to hold no standing access at all — you ask Idira for AWS access at the moment you need it, and it expires on its own afterwards.

  • Everyone
  • ⏱️ ~10 minutes
  •  

The idea 💡

A long-lived access key is a bet: nobody will ever leak this, for as long as it exists. Zero standing privileges — ZSP — removes the bet instead of hedging it. Between tasks you hold no access to that AWS account whatsoever. Credentials arrive only when you ask, only if policy says you may, only for a few hours — and every request is recorded against your name.

Say the phrase to yourself once, because it is exactly literal: zero standing privileges means that right now, before you run anything on this page, your entitlement to that account is nothing. 🫙

🪄 You have done this once already. In Lesson 06 the portal handed you credentials starting with ASIA and a session token. Those were temporary too. The difference now: you are going to ask for access you don't currently have, from the terminal, through the agent.

Steps

1

Give your agent the skills

A skill is a short instruction sheet you hand the agent so it knows how to do a specific job properly. We wrote two for you: idsec and zsp-aws.

From inside sandbox-app, still outside the agent:

mkdir -p .claude/skills
cp -R ../skills/idsec ../skills/zsp-aws .claude/skills/
ls .claude/skills
New-Item -ItemType Directory -Force .claude\skills | Out-Null
Copy-Item -Recurse -Force ..\skills\idsec, ..\skills\zsp-aws .claude\skills\
dir .claude\skills

You should see both folder names listed. Open .claude/skills/zsp-aws/SKILL.md and read it — it is one page of plain English. That is all a skill is. No code. In optional Lesson 12 you can write your own.

2

Check the CLI is there

idsec version

You should get a version number. This is a single file — no installer, no admin rights, nothing added to your system. 🪶

If you get “command not found”, you are probably not in the folder where you extracted it. 🙋 Raise your card.

🖥️ On a managed laptop, something decides whether this may run at all. idsec is a privileged tool: anyone who can run it can ask for cloud access. So the endpoint is a control point in its own right — and that is Idira Endpoint Privilege Manager (EPM), which enforces least privilege, application control and credential theft protection on the machine itself. Its application control policies decide which executables are allowed to run and for whom; a blocked one can be routed through a Request for authorization approval flow instead of just failing, and every one of those policy decisions lands in EPM's audit events. 📋

This is not hypothetical for this room: if your own laptop refused to run idsec during the prework, that is this control working as designed. The three layers are worth saying as one sentence in front of a client 🎯 — EPM governs which tool may run on the endpoint, Secure Cloud Access governs what access that tool can obtain, and for how long, and Secrets Manager holds whatever cannot be eliminated.

3

Log in

idsec login

Follow the prompts, using the login on your numbered card 🎟️. Usually this happens right in the terminal — your password, then a multi-factor check if your tenant asks for one. If a browser window opens instead, sign in there and come back to the terminal.

Do not run idsec configure again — you did that in the prework, and running it again would overwrite your settings.

4

Let the agent do the rest

Start the agent:

claude

Then ask, in plain English:

Use the zsp-aws skill to get me AWS access with zero standing privileges.
Show me what targets I am allowed before you elevate into anything.

Watch what it does. It will:

  1. read the skill 📖
  2. run idsec sca cloud-access list-targets --csp aws and show you the list
  3. ask which one you want, or confirm the only one
  4. run the elevate command for you

Approve each command when it asks. ✅ Read the commands before you approve them — that habit is worth more than anything else on this page.

🕵️ Notice you never learned the flag names, the account number or the role ARN. The skill knew the shape of the commands and the CLI supplied the values. That is the difference between an agent with a skill and an agent guessing.

5

Collect your temporary credentials

Elevation gives you the right to use a role. Now pick up the credentials for it.

Leave the agent with /exit — environment variables have to be set in the terminal itself, and the agent cannot do it for you. Then:

  1. Go back to your AWS portal tab (awsapps.com/start/#) and refresh 🔄
  2. Your newly elevated role now appears in the list — it was not there before
  3. Click Access keys next to it
  4. Choose your tab — macOS and LinuxPowerShell — and copy Option 1: Set AWS environment variables 📋
  5. Paste into your terminal and press ReturnEnter

This replaces the credentials from Lesson 06 with your elevated ones. Everything keeps working — including the agent.

6

Prove who you are now

python -c "import boto3; print(boto3.client('sts').get_caller_identity()['Arn'])"

You will get a long line ending in something like assumed-role/<the-role-you-elevated-into>/<your-name>.

✅ Read that carefully. Two things are true at once: you are in that AWS role, and your own name is attached to the session. A shared access key can never tell you that second part. 🕵️

What this fixes — and what it doesn't 🧭

Be precise about this, because it is exactly the sort of thing that gets overclaimed in a slide:

  • ✅ AWS access — no key needed, ever again. That is real elimination.
  • ❌ GitHub token, Slack webhook, database password — completely untouched. They are still sitting in config/integrations.json. They need a vault, which is a different tool and a different session.

Three out of four secrets are still there when you finish this lab. Say that out loud when you show this to your team. 🫱
