Skills: ZSP by Idsec CLI 🎫

You will ask for AWS access you do not have, be granted it by policy, and use it under your own name. No key is stored anywhere. A skill is what tells your agent how to do it.

  • Everyone
  • Zero standing privileges
  •  

The idea. A long-lived access key is a bet: nobody will ever leak this, for as long as it exists. Zero standing privileges, or ZSP, removes the bet rather than hedging it. Between tasks you hold no access to that AWS account whatsoever. Credentials arrive when you ask, if policy says you may, and they expire on their own a few hours later. Every request is recorded against your name.

Say the phrase to yourself once, because it is literal. Zero standing privileges means that right now, before you run anything on this page, your entitlement to that account is nothing.

🪄 You have done this once already. In Lesson 07 you ran one command and got credentials that expire. We wrote that command for you, with the account number and the role already in it. This time nobody writes it for you. The agent finds out what you are allowed, and writes the command itself.

🪶 Notice what nobody had to set up for this. Before you start, look at what is not on the prerequisite list for the eight steps below:

  • No OIDC provider. Nobody registered an identity provider in that AWS account.
  • No IAM trust policy. There is no trust relationship written to say which external identities may assume which role.
  • No role per person. Sixty attendees, and nobody created sixty roles or sixty mappings.
  • No CloudFormation, Terraform or bootstrap stack. Nothing was deployed into the account to make this work.

You logged in to Idira. That is the whole of your side of the setup. Secure Cloud Access brokers the request itself, so the account does not need to be taught about you in advance.

Worth remembering for client conversations. "How much do we have to build first?" is usually the second question you get asked, right after "how does it work?" The honest answer is that federation plumbing is what Secure Cloud Access replaces. You do not have to build it before you start.

Your Tasks

Give your agent the skills

A skill is a short instruction sheet for one job. We wrote three for you: idsec, zsp-aws and zsp-azure.

From inside sandbox-app, still outside the agent:

New-Item -ItemType Directory -Force .claude\skills | Out-Null

Each one is a page of plain English with no code in it at all, and that is all a skill is. In optional Lesson 12 you can write your own.

3

Check the CLI is there

idsec version

You should get a version number.

“command not found”? Setup step 5 was skipped, or your PATH change needs a new terminal. Run the setup script from the workshop folder, then open a new terminal and try again.

cd ~/Downloads/sko27-japac-idira-ai-workshop
bash check-prereqs.sh
cd $HOME\Downloads\sko27-japac-idira-ai-workshop
.\check-prereqs.ps1

A new terminal holds no credentials, so redo your Lesson 07 elevate command there. Raise your card if the script cannot download the binary, or if idsec is found but refuses to start.

🖥️ Why a managed laptop may block this. idsec is a single file that needs no admin privilege. But it reaches the Idira Identity Security Platform, and anyone who can run it can ask for cloud access. Idira Endpoint Privilege Manager (EPM) decides which programs may run, and can send a blocked one to an approval flow instead of failing it. If your own laptop refused to run idsec during setup, that was this control working as designed.

4

Log in

idsec login

Sign in with your own CYBRWorld account, the one ending in @cyberarklab.com. Your tenant is demo.cyberark.cloud. Usually you type your password and a multi-factor code in the terminal. If a browser window opens instead, sign in there and come back to the terminal.

Already logged in from Lesson 07? You do not need to do it again.

👥 Logged in to a different tenant? Make a second profile, a named set of connection settings, and log in with that one:

idsec configure --profile-name cybrworld
idsec login --profile-name cybrworld

Then add --profile-name cybrworld to every idsec command on this page. idsec profiles list shows what you have.

“No profile found”? Your profile is in another folder. On Windows, idsec looks for its profile and your login in the folder you are standing in, unless IDSEC_PROFILES_FOLDER and IDSEC_KEYRING_FOLDER are set. Setup sets both for you. If your setup ran before that, run the setup script again from the workshop folder.

cd $HOME\Downloads\sko27-japac-idira-ai-workshop
.\check-prereqs.ps1

It moves your profile and your login to two fixed folders. Then come back and check it:

cd sandbox-app
idsec profiles list

The list includes idsec.

Do not run idsec configure again on your existing profile. You did that during setup, and running it again would overwrite your settings.

📖 The full CLI documentation. cyberark.github.io/idsec-cli-golang.

5

Let the agent do the rest

Start the agent:

claude

The bottom line should say auto. If it does not, press Shift + Tab until it does.

Then ask, in plain English:

Use the zsp-aws skill. Show me which AWS targets I am allowed, then print the one command I should run myself to get credentials for the target with most privileges. Do not run that command.

Watch what it does. It will:

  1. read the skill
  2. run idsec exec sca cloud-access list-targets --csp aws and show you the list
  3. ask which one you want, or confirm the only one
  4. print an elevate command with your account number and role already in it, and stop there

Read that command before you go on. Copy it.

Agent says your login expired? Your login is in another folder, not gone. On Windows idsec remembers a login per folder, unless IDSEC_KEYRING_FOLDER is set. Leave the agent with /exit, then run setup again from the workshop folder.

cd $HOME\Downloads\sko27-japac-idira-ai-workshop
.\check-prereqs.ps1

Say yes when it offers to pin the folders and to log you in. Then start the agent again from that same window, so it inherits the two folders:

cd sandbox-app
claude

Ask again. The agent lists your targets.

💡 Notice. You never learned the flag names, the account number or the role ARN. The skill knew the shape of the commands and the CLI supplied the values.

🛑 Why it stops there. The skill tells it to print that command, not run it. Credentials the agent fetches would sit in its context and in its transcript. Yours go into your terminal instead. The rule to take back to work: let the agent find out what you may do, and keep the secret out of it.

6

Run the command yourself

Leave the agent:

/exit

Environment variables have to be set in the terminal itself. The agent cannot do it for you.

Now paste the command the agent printed and press ReturnEnter. It looks like this:

eval "$(idsec exec sca cloud-access elevate --csp aws --workspace-id <account> --roleIds <role-arn> --raw | jq -r '.response.results[0].accessCredentials | fromjson | "export AWS_ACCESS_KEY_ID=\(.aws_access_key)\nexport AWS_SECRET_ACCESS_KEY=\(.aws_secret_access_key)\nexport AWS_SESSION_TOKEN=\(.aws_session_token)"')"
idsec exec sca cloud-access elevate --csp aws --workspace-id <account> --roleIds <role-arn> --raw | jq -r '.response.results[0].accessCredentials | fromjson | [.aws_access_key, .aws_secret_access_key, .aws_session_token] | @tsv' | ForEach-Object { $ak,$sk,$token = $_ -split "`t"; $env:AWS_ACCESS_KEY_ID=$ak; $env:AWS_SECRET_ACCESS_KEY=$sk; $env:AWS_SESSION_TOKEN=$token }

Use the agent's version, with the real account and role in it, not this one. Nothing prints. That is success.

This replaces the credentials from Lesson 07 with your elevated ones. The agent will not run in this role, and step 8 puts it back.

7

Prove who you are now

python -c "import boto3, urllib3; urllib3.disable_warnings(); print(boto3.client('sts', verify=False).get_caller_identity()['Arn'])"

verify=False turns off the TLS certificate check. Some corporate networks inspect traffic, and the check fails on this call. Do not copy that switch into real code.

You will get a long line ending in something like assumed-role/<the-role-you-elevated-into>/<your-name>.

✅ Read that carefully. Two things are true at once: you are in that AWS role, and your own name is attached to the session. A shared access key can never tell you that second part.

8

Put your lab credentials back

Run this in your terminal, not in the agent.

The role you elevated into cannot reach Bedrock, so claude will not start. This command puts back the lab credentials from Lesson 07.

eval "$(idsec exec sca cloud-access elevate --csp aws --workspace-id 409556437035 --roleIds arn:aws:iam::409556437035:role/CW-SCA-AdminAccess --raw | jq -r '.response.results[0].accessCredentials | fromjson | "export AWS_ACCESS_KEY_ID=\(.aws_access_key)\nexport AWS_SECRET_ACCESS_KEY=\(.aws_secret_access_key)\nexport AWS_SESSION_TOKEN=\(.aws_session_token)"')"
idsec exec sca cloud-access elevate --csp aws --workspace-id 409556437035 --roleIds arn:aws:iam::409556437035:role/CW-SCA-AdminAccess --raw | jq -r '.response.results[0].accessCredentials | fromjson | [.aws_access_key, .aws_secret_access_key, .aws_session_token] | @tsv' | ForEach-Object { $ak,$sk,$token = $_ -split "`t"; $env:AWS_ACCESS_KEY_ID=$ak; $env:AWS_SECRET_ACCESS_KEY=$sk; $env:AWS_SESSION_TOKEN=$token }

Nothing prints. That is success.

🧪

Optional: the same thing, for Azure

Secure Cloud Access is not AWS only. Start the agent again and ask:

Use the zsp-azure skill. Show me which Azure targets I am allowed, then print the elevate command for an Azure role I am entitled to.

Leave the agent and run the command it prints. You get back a sessionId and nothing else. There is no access key, nothing to export, and nothing to clean up. The role is active for your own Azure sign-in, and it expires on its own.

That response holds no secret, so you can paste it back to the agent and ask what it means.

This step changes nothing about the sandbox app, which is an AWS application. One CLI, one login and one audit trail cover more than one cloud.

🧪

Optional: now remove the secret

The app still has an AWS key in it. Elevation made that key unnecessary, so delete it.

Lesson 14 is the follow-up to this one. You point an agent at the same sandbox-app, and it takes the key out while keeping the app working. Do it after the workshop if you run out of time here.

What this fixes, and what it does not

One of the four secrets is now gone. The other three are untouched, and saying so is what makes the first claim credible.

  • Fixed: AWS access. No key is needed, ever again. The secret is gone rather than moved somewhere safer.
  • Not fixed: GitHub token, Slack webhook, database password. Completely untouched, and still sitting in config/integrations.json. They need a vault, which is a different tool and a different session.

Three out of four secrets are still there when you finish this lab. Say that out loud when you show this to your team.

Three layers, and one sentence for a client. Endpoint Privilege Manager governs the agents and tools that run on the laptop, Secure Cloud Access and Secure Infrastructure Access govern the access they can obtain, and Secrets Management governs your machine identities everywhere else.

Where Idira fits

🧨 The risk you just saw. The elevation worked because a skill told the agent which commands to run. A Markdown file ended in a privileged CLI running.

What answers it

Secure Cloud Access
Issues the AWS access on request and expires it soon after, so the key in the sandbox app needs no replacement.
Endpoint Privilege Manager
Governs which programs may run, and with what privilege. A skill is only a document until it runs idsec.

Key takeaways

  • You held nothing, then you held something, and it expires. Before this page your entitlement to that account was zero. Access arrived because policy said it could, and it goes away on a clock.
  • Your name is on the session. A shared access key can never tell you the second half of assumed-role/<role>/<you>.
  • A skill is a page of plain English, and it ends in a privileged command. The agent knew the flags because a Markdown file told it. That is convenience and it is privilege at the same time.
  • Nobody built federation plumbing first. No OIDC provider, no trust policy, no role per person. That is the answer to "how much do we have to build before we start?"
