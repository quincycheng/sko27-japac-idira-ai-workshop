First: find the secrets yourself 🕵️

In a moment you will ask an agent to hunt for hardcoded secrets in a small, deliberately awful repo. Before you do — beat it to the punch. Do it by hand, the way you would in a customer's codebase.

🧪 The rules. Everything the agent can see lives in ai-harness-app/sandbox/. Six files, none longer than 40 lines. Every secret in there is a well-known fake — publicly documented example values — so nothing sensitive is on your laptop. ⚠️ Give yourself three minutes, then stop.

1

Look for yourself — no AI 🙅

From the ai-harness-app folder:

ls -la sandbox
grep -rn "KEY\|SECRET\|TOKEN\|PASSWORD" sandbox
Get-ChildItem sandbox -Force
Select-String -Path sandbox\* -Pattern "KEY|SECRET|TOKEN|PASSWORD"

Or just open the files in an editor and read them. Either is fine — reading is the point.

Write down two numbers before you go on: how many files hold a secret, and how many secret values you found in total. 🔢 No peeking below.

🙈 Notice what ls alone misses. One of the two guilty files starts with a dot, so it is invisible to plain ls, to Finder, and to a lot of scanners. The -la / -Force above is doing real work.

🗣️ The line worth stealing for a customer conversation. “It is not better than your scanner at pattern-matching — it is worse. What it does that your scanner cannot is decide what to look for next. Which is also why you cannot audit it by reading its rules: it has none.”

How the loop works 🔁

1 · The tool definition — a schema, and nothing more 
TOOLS = [
    {
        "name": "search_code",
        "description": "Regex-search the repo. Returns matching 'file:line: text' rows.",
        "input_schema": { ... "pattern": {"type": "string"} ... },
    }
]

A tool is two things that must agree: this JSON description, which is all the model ever sees, and a Python function, which is what actually runs. The model cannot see the code, cannot change the code, and cannot invent a tool that is not on this list.

🔐 So your tool list is your attack surface. Word for word, that is the same conversation as “what can this service account do?” — which is why this stuff is a privilege problem wearing an AI costume.

2 · The loop, and the one line that ends it 
while True:
    response = client.messages.create(
        model=MODEL, max_tokens=2048,
        tools=TOOLS, messages=messages,
    )
    ...
    if response.stop_reason != "tool_use":
        break

Remember end_turn from Stage 1? Now the model can stop for a second reason: tool_use, meaning “I want something run before I continue.” That one extra value is what makes agents possible. 🔑

And notice while True — nothing bounds this. If the model keeps asking, the loop keeps going, forever, spending money. Stage 3 fixes it. ⛔

3 · Give the whole turn back, tool request included 
messages.append({"role": "assistant", "content": response.content})

The model's tool_use block goes back into the transcript intact. Drop it and the result you send next has nothing to attach to, and the API rejects the whole request. Half the pain of writing your first harness is this bookkeeping. 📎

4 · Where the security actually lives 
for block in response.content:
    if block.type == "tool_use":
        pattern = block.input.get("pattern")
        if not pattern:
            output = "error: 'pattern' is required and must be non-empty."
        else:
            output = search_code(**block.input)

Read that if again. The model asked; our code decided. That gap is the only place safety can live. Here it is only checking for an empty argument, but the same gap is where you would put an allowlist, a path check, an approval prompt, or an audit log. Stage 5 pushes on it hard.

Note too that a bad request comes back as a normal result the model can read — "error: 'pattern' is required" — not a crash. An agent that can see its own mistakes recovers from them. 🩹

5 · The result goes back as if the user said it 
tool_results.append({
    "type": "tool_result",
    "tool_use_id": block.id,   # must match the request
    "content": output,
})
messages.append({"role": "user", "content": tool_results})

Here is the sentence to remember for the rest of the day: 🚨 the contents of the files you scanned are now in the user role. To the model, the file's text and your instructions arrive in exactly the same stream, with no marker saying “this part is only data”.

If an attacker controls a file the agent reads, the attacker is typing into your conversation. That is prompt injection, it is a design property rather than a bug, and it is Stage 5. 🎣
