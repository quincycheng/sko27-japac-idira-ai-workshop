The Identity Broker 🛡️

In Lesson 08 you gave your agent a short-lived key to AWS. Now do something better: give it access to a tool while it holds no key at all — and be able to prove, afterwards, exactly what it did and who asked.

  • Everyone
  • ⏱️ ~12 minutes
  •  

🎯 This is the lesson you will demo. You are a Domain Consultant. Everything else today was you learning to use an agent. This is the part a client will ask you to show them on a screen share — so we go slower, name every button, and finish with a five-minute demo script you can reuse.

The problem it solves

Today your agent needed one thing: AWS. Real agents need ten — a ticketing system, a directory, a code host, a database, a wiki. The naive answer is to give the agent a credential for each one. Now re-read Lesson 07 and notice you have just rebuilt integrations.json, except this time the thing holding all the keys is a program that acts on its own. 😬

The Idira Identity Broker sits in the middle of every call. It authenticates the agent, checks a policy, forwards the call, and writes down what happened. Three consequences, and these are the three sentences to say to a client:

  • 🔐 The agent never holds the credential. It holds a connection.
  • 📋 Every tool call is audited — including the ones that were refused.
  • 🔴 There is one switch. Flip a server to Disabled and every connected agent loses it immediately.

Steps

1

Point your agent at the Broker

Your trainer has registered an MCP server in the tenant for you. It has a Gateway URL, which looks like this:

https://<region>.data.aigw.cyberark.cloud/mcp/<server-name>

That host is the Broker, not the tool. Nothing about the tool's own address appears anywhere on your laptop. 👀

Take the URL, Client ID and Client Secret from the screen (or your card) and run this outside the agent — one line, all on one line:

claude mcp add --transport http --scope user idira-broker <GATEWAY-URL> --client-id <CLIENT-ID> --client-secret

--client-secret takes no value on the line — it prompts you, so the secret never lands in your shell history. Paste it when asked. 🤫

🪪 Where those come from. When an administrator registers an AI agent in Idira, that is what issues the Client ID and Secret. They are the agent's identity, not a key to any tool — which is why it is safe for sixty people to be handed one and why it is the thing that makes the audit trail say a name instead of “something connected”.

--scope user means the connection follows you into any folder, so the optional lessons still have it.

2

Authenticate as yourself 🙋

Start the agent and open the MCP panel:

claude
/mcp

You will see idira-broker listed as needing authentication. Choose it. Your browser opens; sign in as your own numbered workshop user and approve.

Back in the terminal the tools appear by themselves. Type /mcp again to list them. 🎉

💡 Stop and notice what just happened. You did not type a password for the tool. You proved who you are to Idira, and Idira decided what the agent may do. The agent received permission, never a credential. That single sentence is most of the product.

🧭 If the browser page fails to load after you approve, look at the address bar. A URL starting http://localhost: with ?code=… in it means the handshake worked; the agent picks it up. If it truly hangs, /exit, run claude again, and retry /mcp.

3

Use a tool through the Broker

Ask the agent, in plain English, to do something with the server you just connected — for example:

List the tools you can reach on the idira-broker MCP server, then use one
of them to answer a simple question. Tell me which tool you chose and why.

Approve the tool call when it asks. ✅

🔍 The detail that matters for your demo. Idira discovers the tools on a server the first time an agent connects to it. Until then the console shows Not discovered yet for that server's tool count. So “connect once, then write the policy” is the right order — and if a client says their tool list is empty, this is why.

4

Find yourself in the audit log 📋

Your trainer will put the audit view on the big screen. Find your own call — you are looking for four things in one record:

The record namesWhy a client cares
👤 The human who initiated it“An agent did it” is not an answer an auditor accepts
🤖 The registered agentTells you which of your agents to suspend
🧰 The tool and serverScopes the blast radius precisely
✅❌ Success or failureRefused attempts are the interesting ones

Every time an agent runs a tool, the attempt is recorded — including whether it succeeded or failed. Denied attempts are how you spot an agent probing beyond its remit. 🚩

5

Watch the kill switch 🔴

Now the part the whole room does together. Your trainer will set the MCP server to Disabled in the console. When they say go, ask your agent to use the tool again.

Try that same tool again.

It fails. For everyone. At once. 🛑 Then the trainer re-enables it and it works again.

🔥 Say this out loud, because it is the sales point. Sixty agents on sixty laptops lost access to that tool in one click, from one screen, with no credential rotation, no code change, and no need to know where any of those agents were running. Ask a client how long that takes them today. ⏱️

How access is actually decided 🧩

Connecting is not the same as being allowed. Idira is deny-by-default: a request is permitted only if some policy you wrote allows it. And a policy only matches when both halves line up — the principal making the request and the resource being touched.

The four steps, for when you are the one clicking

You do not have the admin role today, so read this as your demo script. In the console, go to Manage > Policies > AI agents access and click Create policy:

StepWhat you setThe choice worth explaining
1 · General details Policy name, description, owners, tags. Owners and tags are how this stays manageable at a hundred policies. Set them.
2 · MCP servers and tools + Add MCP servers, then pick the tools. Select specific tools (the default) denies anything discovered later. Allow all current and future tools keeps working when the server adds a tool — convenient, and a standing grant nobody reviews.
3 · AI agents + Add AI agents — the agents users may work through. Same trade-off again: Allow all current and future AI agents means tomorrow's newly registered agent inherits this access with nobody approving it.
4 · Users and roles + Add users and roles, filtered by Type and Source. Sources include Idira Cloud Directory, Okta and Entra ID. The Everyone role covers all users in one entry — handy for a lab, rarely right in production.

Then Done. Two enforcement facts to keep in your pocket, because they are the top two support questions:

  • A server or an agent can be added to a policy while still disabled — but both must be enabled before anything actually works. 🔌
  • Tools must be discovered before you can allow them individually. Before the first connection there is no tool list to pick from, so your only option is Allow all current and future tools. Connect once, then come back and narrow it down. 🔁

🔑 Who can do this. Creating and managing AI agent access policies needs the Secure AI Admin role. If a client tells you the menu is missing, that is the answer — not a bug.

Registered vs pass-through 🕵️

An agent that was never registered can still reach a server. Idira calls that traffic pass-through, and the difference shows up exactly where it hurts:

🕵️ Pass-through (unregistered)🪪 Registered agent
Visible? Yes — the Broker still sees the traffic. Yes.
Audit says “This server was accessed, these tools were used.” The human, the agent, the server, the tools.
During an incident You know something happened. You cannot say who or what. You can suspend one agent and one user, and prove the scope.

On-behalf-of: the question every client asks 🙋

Eventually someone in the room says: “if the agent can read any ticket, hasn't every user just become an admin?” That is the right question, and it has a name.

ModeWho the tool thinks is callingConsequence
Service identity The Broker itself Simple, but every user gets the same permissions — the union of everyone's.
On-behalf-of (OBO) You, the human who asked The tool applies your permissions. The agent cannot exceed what you could do yourself.

You already did the OBO half in step 2 — that browser sign-in is you injecting your identity into the chain. The agent inherits your access, not the platform's, so your existing access model keeps working unchanged. 🎯

Your five-minute client demo 🎬

You just lived through it, so you can run it. In this order:

  1. Show the pain first. Open config/integrations.json from Lesson 07. “This is one small app. Three systems. Now imagine an agent that needs ten.” 😬
  2. Connect an agent to a tool and point out loudly that you typed no credential — only proved who you were.
  3. Run one tool call, then show that call in the audit log with the user's name on it.
  4. Disable the server while they watch, re-run, and let it fail. This is the moment that lands. 🔴
  5. Open the policy and show the three lists. “Deny-by-default. Nothing works unless something here says so.”
  6. Close with the one question: “Today, how would you answer an auditor asking which of your agents touched this system last Tuesday?” 🧭
