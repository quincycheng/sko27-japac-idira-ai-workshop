MCP: AI Agent Identity Broker 🛡️

By the end of this lesson you will know how to govern AI agents with the Idira AI Agent Identity Broker. You will make one tool call that works and one that is refused. You will then find both of them in the audit log, with your own name on them.

🎯 This is the lesson you will demo. You are a Domain Consultant. Everything else today was you learning to use an agent. This is the part a client will ask you to show them on a screen share. So you do it three times over, as the user, as the security professional and as the auditor.

The problem it solves. Today your agent in this workshop needed one thing only: AWS. Real agents need ten: a ticketing system, a directory, a code host, a database, a wiki. The obvious answer is to give the agent a credential for each one. That rebuilds integrations.json from Lesson 08, except now a program that acts on its own is holding all the keys.

The Idira AI Agent Identity Broker sits in the middle of every call. It authenticates the agent, checks a policy, forwards the call, and writes down what happened. Three consequences. These are the three sentences to say to a client:

  • The agent never holds the credential. It holds a connection.
  • Every tool call is audited, including the ones that were refused.
  • There is one switch. Flip a server to Disabled and every connected agent loses it immediately.

Your Tasks

Three acts. You use an agent, you read the policy that governed it, then you read the audit trail it left behind.

🔑 One tenant, all the way through. Everything here runs against CYBRWorld, the tenant you set up in step 6 of setup. There is nothing to switch and no secret to fetch. Sign in as your own account, the one ending @cyberarklab.com. The console is at demo.cyberark.cloud.

You are the user

1

See what your agent can reach now

Start the agent:

claude

Ask it which MCP servers it has:

/mcp

Most people see No MCP servers configured. If you use Claude Code at work you may see your own servers. Either way, there is no Broker in the list. You run this again in step 3.

Now leave the agent:

/exit

The next command runs in your terminal, not in the agent.

2

Connect your agent to the Broker

An administrator has already registered an MCP server for you. Its Gateway URL is the address an agent uses to reach that server through the Broker:

https://demo.data.aigw.cyberark.cloud/mcp/entrasonarmcp

That host is the Broker, not the tool. The tool's own address never appears on your laptop.

Run this in your terminal. It is one line:

claude mcp add --transport http --scope user idira-ai-broker-entrasonar https://demo.data.aigw.cyberark.cloud/mcp/entrasonarmcp --client-id 04e6ab3b-de59-4d1d-a73c-c283f48713b8 --callback-port 8080

It confirms idira-ai-broker-entrasonar was added and names the file it changed. Nothing is authenticated yet. --scope user means the connection follows you into any folder.

✅ There is no secret on this page. The --client-id is the agent's identity, not a key to any tool. This agent is registered as a public client, so there is no client secret to hand out or to leak. Your browser sign-in in step 3 is what proves who you are.

🧭 If step 3 never returns to the terminal, something else is already using port 8080. That port is where the agent waits for the browser to come back. Stop the other process, or run the command again with a free port such as --callback-port 8123. Remove the server first with claude mcp remove idira-ai-broker-entrasonar.

3

Authenticate as yourself

Start the agent and open the MCP panel again:

claude
/mcp

Use the up and down arrow keys to select idira-ai-broker-entrasonar, then press Enter. Choose Authenticate. Your browser opens. Sign in to CYBRWorld as your own account and approve.

The browser says:

Connected
Authentication successful
You can close this tab and return to Claude Code.

Close that tab. The terminal says:

Authentication successful. Connected to idira-ai-broker-entrasonar.

💡 Stop and notice what just happened. You did not type a password for the tool. You proved who you are to Idira, and Idira decided what the agent may do. The agent received permission, never a credential. That single sentence is most of the product.

🧭 If the wrong browser opens, or the wrong profile in it, press c in the terminal to copy the sign-in URL. Paste it into the browser that has your CYBRWorld session. The error will not tell you that this is the problem. If the terminal hangs, restart the agent and try again:

/exit
claude
/mcp
4

Use a tool through the Broker

Ask the agent what it can now do:

What MCP tools are available?

Two tools come back, analyze_domain and beta_features. Each name starts with mcp__idira-ai-broker-entrasonar__, because the name carries the server it came from. Both are described as a proxied version, which is the Broker telling you it sits in the middle.

Now use the first one:

Use the analyze_domain tool on the idira-ai-broker-entrasonar server to analyze the domain paloaltonetworks.com.

Approve the tool call. The answer gives that domain's Entra tenant ID, its mail gateway and a long list of third-party services in use.

💡 Count your credentials. You hold no account on that service and no API key for it. You proved who you were once, in a browser, and the Broker did the rest.

🔍 The detail that matters for your demo. Idira discovers the tools on a server the first time an agent connects. Until then the console shows Not discovered yet for that server. So connect once, then write the policy. If a client says their tool list is empty, this is why.

🧭 If the agent says the server needs re-authorization, your token has expired. Run this and sign in again:

/mcp

Your agent holds a short-lived token, and it stops working on its own. A credential in a config file does not.

5

Ask for the other tool

beta_features was in the list, so the agent will try it. Ask for it:

Use the beta_features tool on the idira-ai-broker-entrasonar server.

Approve the call. It fails, and this is the expected result:

Access denied by access policy: you are not authorized to call tool
"beta_features__entrasonarmcp" on this target. This request was blocked by
the organization's access policies; ask an administrator to grant access.

Nothing on your laptop refused that. The Broker did, and it wrote the attempt down. You find out why in step 8, and you find the record in step 9.

Change hats. Open the console at demo.cyberark.cloud and sign in with the same account. You have read access: you are looking, not changing.

7

Find the MCP server

Go to Manage > Inventory > AI > MCP Servers (direct link). Open EntraSonar MCP.

Read three tabs, in this order:

TabWhat to look for
DetailsThe Gateway URL you pasted, and whether the server is Enabled.
ToolsBoth analyze_domain and beta_features, listed because an agent connected and Idira discovered them.
Connected AI agentsJAPAC-SKO27. The same relationship as step 6, read from the resource instead of the principal.

Discovered is not the same as allowed. Both tools are here. Only one of them worked for you.

8

Read the access policy

Go to Manage > Policies > AI agents access (direct link). Open EntraSonar MCP - Allow.

Read its four parts against the screen in front of you:

PartWhat it setsThe choice worth explaining
1 · General details Policy name, description, owners, tags. Owners and tags are how this stays manageable at a hundred policies.
2 · MCP servers and tools The servers, then the tools on them. This policy names analyze_domain and not beta_features. That one omission is the whole of step 5.
3 · AI agents The agents users may work through. Allow all current and future AI agents means tomorrow's newly registered agent inherits this access with nobody approving it.
4 · Users and roles Who may work through those agents. Sources include Idira Cloud Directory and Entra ID. The Everyone role covers all users in one entry. Handy for a lab, rarely right in production.

🚨 Access is denied by default. No policy grants beta_features to anyone, so nobody can call it. Nothing had to be written to block you. That is the opposite of most systems, where access is open until somebody remembers to close it. It also makes this screen a kill switch: remove the tool, the agent or your role and the calls stop, for every connected agent at once. Disabling the server does the same. Ask a client how long that takes them today.

You can read this policy. You cannot write one: authoring needs the Secure AI Admin role. If a client says this menu is missing for them, that is the answer, not a bug.

How access is decided

The part a client will push on. Three things line up, or nothing happens.

Connecting is not the same as being allowed. Idira is deny-by-default. A policy matches only when both halves line up: the principal making the request and the resource being touched. Both the agent and the server must also be enabled, or no policy applies at all.

Your beta_features call in step 5 failed the resource half. The tool was discovered and the agent was enabled, and it still stopped, because no policy named that tool.

Key takeaways

  • The agent held a connection, not a credential. You proved who you were; Idira decided what the agent could do. Everything else on this page follows from that.
  • Deny-by-default means three things line up or nothing happens: the user, the agent and the tool. You saw it: one tool worked and one was refused, on the same connection, a minute apart.
  • Access is removed from one screen. Take the tool, the agent or the role out of the policy, or disable the server, and every connected agent stops. No rotation, no code change, no knowing where sixty agents were running. That is the sentence a client remembers.
  • The refusal was audited too. A record that names the human, the agent and the tool answers an auditor. A record of what was refused is how you spot an agent going too far.
