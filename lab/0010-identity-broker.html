MCP: AI Agent Identity Broker 🛡️

By the end of this lesson you will know how to govern AI agents with the Idira AI Agent Identity Broker. It shows you which agents are reaching corporate data, and it acts as a kill switch to stop a specific agent reaching a specific resource. You will have done both yourself: one tool call you held no credential for, and one audit record with your name on it.

🎯 This is the lesson you will demo. You are a Domain Consultant. Everything else today was you learning to use an agent. This is the part a client will ask you to show them on a screen share. So you do it twice, once as the user and once as the administrator, and finish with a five-minute demo script you can reuse.

The problem it solves. Today your agent in this workshop needed one thing only: AWS. Real agents need ten: a ticketing system, a directory, a code host, a database, a wiki. The obvious answer is to give the agent a credential for each one. That rebuilds integrations.json from Lesson 08, except now a program that acts on its own is holding all the keys.

The Idira AI Agent Identity Broker sits in the middle of every call. It authenticates the agent, checks a policy, forwards the call, and writes down what happened. Three consequences. These are the three sentences to say to a client:

  • The agent never holds the credential. It holds a connection.
  • Every tool call is audited, including the ones that were refused.
  • There is one switch. Flip a server to Disabled and every connected agent loses it immediately.

Your Tasks

Eight steps, in two halves. In the first half you are a person using an AI agent. In the second half you are the administrator who has to answer for that agent. Tick each one off as you go.

🔑 What you need before you start. This lesson uses the apj-secrets tenant. That is a different tenant from Lesson 09. Sign in with your own account, the one you checked in setup step 9. The Client Secret for step 2 is in the Slack channel #cybr-japac-ts-all. Do not paste it into any other window.

You are the user

1

See what your agent can reach now

Start the agent:

claude

Ask it which MCP servers it has:

/mcp

There is no Broker in the list. Remember that, because you run this again in step 3. Now leave the agent:

/exit

The next command runs in your terminal, not in the agent.

2

Connect your agent to the Broker

An administrator has already registered an MCP server for you. Its Gateway URL is the address an agent uses to reach that server through the Broker:

https://apj-secrets.data.aigw.cyberark.cloud/mcp/entrasonar-mcp

That host is the Broker, not the tool. The tool's own address never appears on your laptop.

Run this in your terminal. It is one line:

claude mcp add --transport http --scope user idira-broker https://apj-secrets.data.aigw.cyberark.cloud/mcp/entrasonar-mcp --client-id e5ba972d-ad32-4c7b-9fcb-c9a24a9cf370 --client-secret

--client-secret takes no value on the line. It prompts you instead, so the secret never reaches your shell history. Paste it from Slack when asked.

It confirms idira-broker was added and names the file it changed. Nothing is authenticated yet. --scope user means the connection follows you into any folder.

🪪 Where the Client ID and Secret come from. An administrator registered an AI agent in Idira. That is what issues them. They are the agent's identity, not a key to any tool. That is why it is safe to hand one to sixty people, and why the audit trail can name the agent.

3

Authenticate as yourself

Start the agent and open the MCP panel again:

claude

Press Shift+Tab a few times until the bottom line says auto. Then:

/mcp

This time idira-broker is in the list, marked as needing authentication. Select it and confirm. Your browser opens. Sign in as your own account and approve.

The browser page says the authentication was successful, and you can close that tab. The terminal says it is connected to idira-broker. Type /mcp once more to list the tools.

💡 Stop and notice what just happened. You did not type a password for the tool. You proved who you are to Idira, and Idira decided what the agent may do. The agent received permission, never a credential. That single sentence is most of the product.

🧭 If the browser step goes wrong. Wrong browser, or wrong profile in it: copy the URL from the terminal into the right one. The error will not tell you that. Page will not load after you approve: a URL starting http://localhost: with ?code=… means the handshake worked and the agent picks it up. If it hangs, /exit, run claude again, and retry /mcp.

4

Use a tool through the Broker

Ask the agent what it can now do:

What MCP tools are available?

One tool comes back. Its name starts with mcp__idira-broker__, because the name carries the server it came from. The tool itself is analyze_domain.

Now use it:

Use the analyze_domain tool on the idira-broker server to analyze the domain paloaltonetworks.com.

Approve the tool call. The tool gathers public information about that domain, including its Microsoft 365 details, and the agent summarises what came back.

💡 Count your credentials. You hold no account on that service and no API key for it. You proved who you were once, in a browser, and the Broker did the rest.

🔍 The detail that matters for your demo. Idira discovers the tools on a server the first time an agent connects. Until then the console shows Not discovered yet for that server. So connect once, then write the policy. If a client says their tool list is empty, this is why.

🧭 If the agent says the server needs re-authorization, your token has expired. Run /mcp and sign in again. Your agent holds a short-lived token, and it stops working on its own. A credential in a config file does not.

7

Read the access policy

Go to Manage > Policies > AI agents access (direct link). The page is titled AI agents access policies.

The list shows each policy's name, the MCP server and AI agents it covers, its owners, when it last changed, and its tags. You can see the blast radius of every policy without opening one.

Open the policy that covers this workshop. This is what decided your tool call was allowed. It has four parts. Read each row below against the screen in front of you:

PartWhat it setsThe choice worth explaining
1 · General details Policy name, description, owners, tags. Owners and tags are how this stays manageable at a hundred policies.
2 · MCP servers and tools The servers, then the tools on them. Select specific tools denies anything discovered later. Allow all current and future tools keeps working when the server adds a tool. That is convenient, and it is a standing grant nobody reviews.
3 · AI agents The agents users may work through. Same trade-off again: Allow all current and future AI agents means tomorrow's newly registered agent inherits this access with nobody approving it.
4 · Users and roles Who may work through those agents. Sources include Idira Cloud Directory, Okta and Entra ID. The Everyone role covers all users in one entry. Handy for a lab, rarely right in production.

🚨 This screen is a kill switch. Remove the tool, the agent or your role from this policy and the calls stop. Every connected agent, at once, from one screen. No credential rotation, no code change, and no need to know where those agents are running. Disabling the MCP server does the same thing. Ask a client how long that takes them today.

You can read this policy. You cannot write one: authoring needs the Secure AI Admin role. If a client says this menu is missing for them, that is the answer, not a bug.

How access is decided

The part a client will push on. Three things line up, or nothing happens.

Connecting is not the same as being allowed. Idira is deny-by-default. A policy matches only when both halves line up: the principal making the request and the resource being touched. Both the agent and the server must also be enabled, or no policy applies at all.

Registered vs pass-through

Registering an agent is optional. The cost of skipping it only shows up on the worst day.

An agent that was never registered can still reach a server. Idira calls that traffic pass-through. Two differences:

  • Pass-through tells you a server was accessed and which tools ran. It cannot tell you who or what did it.
  • A registered agent names the human, the agent, the server and the tool. In an incident you can suspend one agent and one user, and prove the scope.

On-behalf-of: the question every client asks

If the agent can read anything, has every user just become an admin? Two modes, and you used the safe one in step 3.

ModeWho the tool thinks is callingConsequence
Service identity The Broker itself Simple, but every user gets the same permissions: the union of everyone's.
On-behalf-of (OBO) You, the human who asked The tool applies your permissions. The agent cannot exceed what you could do yourself.

Your browser sign-in in step 3 put your identity into the chain. The agent inherits your access, not the platform's, so your existing access model keeps working unchanged.

Your five-minute demo

You just lived through it, so you can run it. Six beats, in this order. The fourth one is the one that lands.

  1. Ask how many AI agents are reaching their corporate data and resources today. Most clients do not know. That is the same wall you hit in Lesson 06.
  2. Connect an agent to a tool and point out loudly that you typed no credential. You only proved who you were.
  3. Run one tool call, then show that call in the audit log with the user's name on it.
  4. Disable the server in your own tenant while they watch, re-run the call, and let it fail. This is the moment that lands. You did not see it today, because nothing in the workshop tenant is changed during the session. Rehearse it before you show it.
  5. Open the policy and show the three lists. “Deny-by-default. Nothing works unless something here says so.”
  6. Close with the one question: “Today, how would you answer an auditor asking which of your agents touched this system last Tuesday?”

Key takeaways

  • The agent held a connection, not a credential. You proved who you were; Idira decided what the agent could do. Everything else on this page follows from that.
  • Deny-by-default means three things line up or nothing happens: the user, the agent and the tool. A partial match is a denial, and the denial is logged.
  • Access is removed from one screen. Take the tool, the agent or the role out of the policy, or disable the server, and every connected agent stops. No rotation, no code change, no knowing where sixty agents were running. That is the sentence a client remembers.
  • Registering the agent is what makes the audit answer a question. Pass-through tells you something happened. A registered agent tells you who, what and how far.
