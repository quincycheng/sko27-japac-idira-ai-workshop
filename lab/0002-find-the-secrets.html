Lesson 2 of 5

Find the secrets 🔎

You have inherited a small app that someone else wrote in a hurry. It does not work. Let the agent tell you why — and then let it tell you what else it noticed.

  • Everyone
  • ⏱️ ~13 minutes
  •  

🧪 Everything in this app is fake. Every key, token and password you are about to find is a public example value. None of them open anything, anywhere. You can read them out loud.

Meet the patient

summarize.py reads a security incident report and asks Claude to summarise it. notify.py is the part that posts that summary to Slack and opens a GitHub issue — today it only prints what it would send, so nothing leaves your laptop. It is the kind of small internal tool that gets written on a Friday and runs for four years.

Steps

1

Run it and watch it fail

In your terminal, outside the agent (press Esc then type /exit if you are still in the chat):

python summarize.py

You will get an error. 💥 Read it. Do not skip past it — the error is the first clue, and reading errors is most of what this job is.

Notice what it does not say. It does not say “no credentials found”. It says the credentials it has were rejected. So the app has credentials. It just has bad ones. Where are they? 🤨

2

Ask the agent, don't go hunting

Start the agent again:

claude

Then paste this in:

Run "python summarize.py". Explain why it fails, in plain English, to
someone who is not a developer. Do not fix anything yet.

The agent will ask permission before running the command. Say yes. ✅ Then read its answer.

It should point you at config/settings.py. Have a look at that file yourself — and look at the comment above the credentials.

😬 That comment. # TODO: move these somewhere safer before we ship this. Whoever wrote this knew. They were not careless, they were busy. This is what almost every real finding looks like.

3

Ask for a proper security review

Now stop looking at the one file you know about, and ask about all of them:

Review every file in this project for hardcoded secrets and credentials.
For each one, tell me: which file, what kind of secret it is, and what an
attacker could do with it. Make a table. Change nothing.

This takes a minute or two. ⏳ While it works, notice what you did not have to do: you did not know the file names, you did not know Python, and you did not know what a Slack webhook looks like.

Now do the same thing the short way. Claude Code has a review built in:

/security-review

Behind that one word is a long, carefully written security prompt — someone else already did the work of remembering what to look for. 💼 Compare its findings with your own table. Did it catch anything you missed? Did you catch anything it missed?

🧭 If it says there is nothing to review. /security-review is built for changes — the work you are about to commit or raise for review. Today's secrets were committed long ago, so on a fresh clone there may be no pending changes to look at. If so, ask for the whole project instead: “run a security review across every file in this project, not just changed ones”. That difference is worth knowing: on Monday, the natural home for this is every pull request, where it reviews exactly what is new. 🔁

See the other three in action

The AWS key is easy to dismiss as an accident. The other three are load-bearing — the app genuinely uses them. Leave the agent (/exit) and run:

python notify.py "Two hosts isolated, no data left the network."

Nothing is sent anywhere — it is a dry run. But look at what it prints: a Slack URL with a token in it, and a GitHub Authorization header. 👀

🚨 Think like a defender for a second. If this folder were zipped and emailed, or pushed to a public repository, or copied onto a build agent — how many systems just got exposed? And how would you ever know which of the four had been used?

6

Ask the question that matters

Back in the agent, paste this:

Of the secrets you found, which ones does this app truly need to store,
and which ones could be replaced by asking for access at the moment it is
needed? Explain the difference.

Its answer sets up the rest of the workshop. There are two completely different fixes hiding in that list, and most people only know about one of them.

The two fixes 🧰

🔒 Onboard it✂️ Eliminate it
What you do Move the secret into a vault. The app fetches it when it starts. Delete the secret. The app asks the platform for access when it runs.
Secret still exists? Yes — somewhere much safer, with rotation and an audit trail. No. There is nothing left to steal, leak, or rotate.
Good for GitHub tokens, Slack webhooks, database passwords — anything with no other way in. Cloud access, where the platform can mint short-lived credentials on demand.
The Idira answer Idira Secrets Manager. The three remaining secrets belong in it — vaulted, rotated, audited, and fetched by the app at run time. Idira Secure Cloud Access, which is what you use in Lesson 3.
Today Named, not done — vaulting is a session of its own. Lessons 3 and 4. 👉

🎤 Say both halves to a client. “Eliminate what you can, vault the rest.” You will leave today with one of the four secrets gone and three still sitting in a config file — deliberately. Those three are exactly the case for Idira Secrets Manager, and being able to say which fix applies to which secret, and why, is the whole skill.

🎸 And about the AI… Ask an agent to “write a script that calls AWS” without saying anything about credentials, and it will frequently put them straight into the file — because that is what most of the code it learned from does. It is getting better, and often reaches for an environment variable instead. But frequently is a bad number when you are shipping sixty times a week. Speed makes review matter more, not less.
