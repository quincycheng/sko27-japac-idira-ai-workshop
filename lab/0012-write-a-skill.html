Write your own skill 📝

The zsp-aws skill you used in Lesson 08 is one page of plain English. Anything you personally know how to do can become one — and then the agent knows it too, every time, without being reminded.

  • ⏱️ ~15 minutes

What a skill actually is

A folder with a SKILL.md file in it. That is the whole format. 🪆

.claude/skills/my-skill/SKILL.md

Inside, a few lines of front matter — a name and a description — then prose. The description is the important part: it is how the agent decides whether this skill applies to what you just asked for. A vague description means a skill that never gets used. 🎯

🧩 Not the same as a tool. A tool is a capability an MCP server gives the agent — something it can now do (Lesson 10). A skill is knowledge about how to do the job properly with capabilities it already has. You will hear these two used interchangeably in the wild. They are not the same, and a client who conflates them will design the wrong thing.

Broad or narrow? Start narrow.

🗺️ Broad🎯 Narrow
Teaches The shape of a thing, and how to discover the rest. One ordered procedure, start to finish.
Today's example skills/idsec/SKILL.md — “here is how this CLI is organised, use --help”. skills/zsp-aws/SKILL.md — “do these five things in this order”.
Fails by Being too vague to change the agent's behaviour at all. Being wrong in a way you notice immediately. Much better. ✅

Open both of those files now, before you write anything. Two minutes of reading saves ten of guessing. 📖

Steps

1

Get a skill for writing skills

Inside the agent, open the plugin browser:

/plugin

Find mattpocock-skills in the marketplace and install it. Among other things it gives you writing-for-agents — a skill whose whole job is helping you write skills. 🪆

2

Pick something you actually know

The best skill is a procedure you have explained to a new colleague more than twice. Candidates from your real job:

  • How your team triages a phishing report 🎣
  • How you check whether a finding is a duplicate 🔁
  • The commands you always run when onboarding a new safe 🔐
  • How you assemble a customer health-check summary 📋
  • Your naming and tagging conventions, so the agent stops inventing its own 🏷️

💡 A Domain Consultant's version. “How I set up a customer demo tenant, in order, with the checks at each stage.” You do that repeatedly, the steps are exact, and the cost of getting step four wrong is an embarrassing demo. That is a perfect narrow skill.

3

Let it interview you

Do not ask it to write the skill. Ask it to interrogate you first — this is the difference between a skill that captures what you know and one that captures what the model guessed:

Using the writing-for-agents skill, help me write a skill that captures how
my team does <the thing you do>. Interview me first, one question at a
time, and do not guess at anything I have not told you.

Answer properly. The awkward questions — “what do you do when that check fails?” — are where the value is, because that is the part you never write down. 🤔

4

Save it and test it cold 🧪

Save the result as .claude/skills/<name>/SKILL.md — the same layout you copied in Lesson 08.

Then the real test. Start a fresh conversation:

/exit
claude

…and ask for the task in your own words, without mentioning the skill. If the description is good, the agent picks it up by itself. If it does not, the fix is almost always the description, not the body. 🔧

🎁 This one is yours to keep. Copy the folder into ~/.claude/skills/ and it follows you into every project on this machine. Nothing about it is workshop-specific — it is a text file you wrote.
