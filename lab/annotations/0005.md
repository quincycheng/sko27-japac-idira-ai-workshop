## 05_harness.py :: def prove_the_controls() -> list:
### Why this function exists at all
until: holds when a file attacks it by surprise.
Every other component in this lesson needs the model to cooperate. This one does not.
It attacks the tool boundary directly, with no model in the loop, using the same
arguments a successful attack would have produced.

Those three refusals are identical on every laptop in the room. The model's behaviour
is the anecdote; this is the evidence.

## 05_harness.py :: # --- assemble the toolbox
### Seven components, one loop, no changes to the loop
until: session, agent, tools.TOOLS, mcp_tools=mcp_tools, mcp_execute=mcp_execute
`harness.build` returns a toolbox and one `execute` function. The loop in `agent.py`
has not changed since lesson 04 — open it and check.

That is the point worth photographing: a harness grows by adding tools and hooks, not
by rewriting the thing that runs them. Everything Claude Code does, it does through a
boundary this shape.

## 05_harness.py :: # Rules + the skills catalogue. Note how little of the skills goes in: two
### Skills cost two lines until they are needed
until: system=(rules + "\n\n" + catalogue).strip(),
The rules go in whole. The skills do not — `skills_catalogue()` returns a name and a
one-line description each. The body of `skills/vuln-report/SKILL.md` arrives only if
the model calls `load_skill`, and then only that one file.

This is lesson 03's trade, spent on purpose this time: you pay for what is in the
window on every turn, so put the index in the window and leave the contents on disk.
Both strings are then joined into the one flat blob you met in lesson 03.

## 05_harness.py :: tools=toolbox,
### The only part that outlives the process
until: memory=True,  # memory.md joins the context.
`memory.md` is read into the context at startup and written by `/remember`. When the
process exits, the toolbox, the transcript and the summary are all gone; that file is
not.

Which makes it the most security-relevant file in the app. Nothing signs it, nothing
reviews it, and anything that ends up in it is quietly trusted tomorrow. An agent
that can write its own memory can poison its own memory — permanently, and out of
sight.

## harness.py :: SECRET_NAMES = (".env", "id_rsa", ".pem", "credentials")
### The only component here that is a control
until: "can change that."
Five of the seven components are text in a context window. The model reads them, and
reading is a request. A rule can be argued with. A skill can be ignored. A memory can
be poisoned.

This cannot. It is a Python function that runs before the call, returns a refusal
string, and no wording anywhere in the conversation reaches it. Ask the agent to read
`sandbox/.env` in the chatbox and watch: it refuses, and it asks nobody.

## harness.py :: def audit_every_call(name, tool_input):
### Two hooks: one that watches, one that stops
until: HOOKS = [audit_every_call, deny_secret_reads]
`audit_every_call` never blocks anything — it appends a JSON line to `audit.log` for
every call, which is the difference between "the agent did something" and "we can
prove what the agent did".

`deny_secret_reads` blocks. Both run before the tool, in order, in code, and the list
at the bottom is what wires them into the loop. That list is the honest answer to
"how do we secure our AI agents": not a better prompt library, but what runs in the
loop regardless of what the model wants.

## harness.py :: def execute(name, tool_input):
### Where somebody else's tools plug in
until: return f"Tool '{name}' raised {type(error).__name__}: {error}"
One function, four outcomes. Names starting with `mcp__` are not ours: they are
dispatched over JSON-RPC to a separate MCP server process, which decides for itself
what to do. Then the harness's own handlers, then lesson 04's local tools, and a
`try` so that a broken tool returns an error string instead of killing the loop.

The loop in `agent.py` neither knows nor cares which branch ran. That is what makes
MCP useful, and it is also the supply-chain question in one line: those tool
descriptions and those tool results go straight into your model's context, and they
came from someone else's server.

## harness.py :: # What the child gets, and what it does not.
### The subagent inherits the tools — and the hooks
until: hooks=HOOKS,
A subagent gets its own context window, its own bill, and no memory of the parent
conversation. What it must **not** get is a way around the parent's controls.

Note the two deliberate choices, both visible in the arguments: it gets the same
`hooks=HOOKS`, and `child_tools` does not include `SUBAGENT_TOOL`, so it cannot spawn
children of its own. A hook that guards the parent but not its children is a control
with a documented bypass, reachable by any model that can write the word "delegate".
This is exactly the hole that opens up when a team adds subagents to a system whose
policy enforcement was written for one agent.

## mcp_client.py :: PROTOCOL_VERSION = "2026-07-28"
### An MCP server that asks you for nothing
until: PLAYGROUND_URL = "https://mcpplaygroundonline.com/mcp-stateless-server?rev=2026-07-28"
No token, no key, no account — just a protocol version and a URL. That is convenient
for a workshop and it is the whole problem in two lines: an unauthenticated internet
service, handing live tool schemas and live tool output to an agent that can read your
repository.

Expect your proxy to block it, and treat the block as the finding rather than the
obstacle. The version of this question a customer will ask you is "who is the agent,
and who said it could call that?" — Idira Identity for the token, the Agentic AI
Broker for the gateway that mints and audits it.

## mcp_client.py :: # Prefix every MCP tool so a name collision with tools.py is impossible
### The only thing telling you where a capability came from
until: PREFIX = "mcp__"
Our four tools and a stranger's tools end up in one flat list, and the model picks
between them with no idea which is which. The prefix is not a security boundary — it
is a naming convention that makes the ⚙ lines readable, so the room can see which
calls left the building.

Claude Code uses the same convention, for the same reason. When you audit an agent's
toolbox, this prefix is where you start counting.

## mcp_client.py :: for _hop in range(max_round_trips):
### A cap on how many times a server may say "ask me again"
until: return f"Gave up after {max_round_trips} round trips to '{name}'."
The 2026-07-28 revision is *stateless*: the server keeps nothing between calls, so
mid-operation state comes back to us in a signed `requestState` blob that we echo
verbatim on the follow-up. We verify nothing about that signature — it is for the
server to check when we hand it back.

Say the shape of that trust out loud: the server protects itself from us, and nothing
in the protocol protects us from the server. An unbounded round trip is a
denial-of-service a server can inflict on its client, which is why this is a `for`
with a limit and not a `while`.

## mcp_client.py :: # Their words, verbatim, straight into our model's context. A
### Their words, straight into your model's context
until: "input_schema": tool.get("inputSchema")
These two fields are the MCP supply-chain question. A tool description is
instructions the model reads and acts on, and we have just relayed someone else's,
unread, into the same flat token stream as our rules — along with a schema that tells
the model what arguments to invent.

A hostile file is one thing. This is a hostile *tool catalogue*, and it arrives before
the agent has done anything at all.
