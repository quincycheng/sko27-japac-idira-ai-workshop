Build something AFK 🛋️

You will be interviewed by an agent, approve a spec and a set of tickets, then leave the room while it builds and reviews its own work. The last phase runs without you.

Worth watching on the train home.

The idea: front-load the humans. The usual way people vibe-code is a conversation: ask, look, correct, ask again. It works, and it requires you to be present for the whole build. That does not scale to anything real, because you are the bottleneck.

So group the human interactions differently. Put every decision, every ambiguity and every correction into an early phase where you are fully engaged. Then hand over a plan so clear that the agent needs nothing else from you, then go to a meeting.

Why the tickets have to be small. An agent has a context window, meaning a fixed amount it can hold in mind at once: your instructions, the files it has read, and everything it has said so far. It does not forget neatly when that fills up. It drifts. It rediscovers a file it already read, contradicts a decision from twenty minutes ago, and re-solves a solved problem.

This is what people mean by context engineering: deliberately managing what is in front of the agent. The most effective move is the one this workflow makes for you. Each ticket is a vertical slice sized to fit in one fresh context window.

One big ticketMany small tickets
Context Fills up, then degrades for the rest of the job. Each one starts clean. No inherited confusion.
When it goes wrong You find out at the end, and it is all tangled together. You find out after one slice, and only that slice is affected.
Recovering Re-explain everything to a confused agent. Re-run one ticket in a fresh window.
Your review A wall of changes nobody reads properly. A diff you can actually hold in your head.

“Vertical” matters too: each slice goes all the way from one end to the other and genuinely works when it is done, rather than being a layer that only makes sense once three more layers exist.

🧪 This workflow expects a real project. It works best where there is git, and where tests and a type check can tell the agent whether it succeeded. That feedback is what makes unattended work safe. Today's workshop repo is in git, so you are fine. In an empty folder, ask the agent to set up git first.

Your Tasks

Steps 2 to 4 need all of your attention. Step 5 needs none of it.

1

Install the harness

Inside the agent:

/plugin

Install mattpocock-skills from the marketplace. Then run its setup once, so it knows where to keep specs and tickets:

/setup-matt-pocock-skills

⌨️ Type these as slash commands. Several of these skills are deliberately not auto-selectable. The agent will not decide on its own to start writing tickets. You invoke each phase explicitly.

Type / and start typing the name, then pick it from the menu. If your terminal shows it with the plugin in front, as /mattpocock-skills:grill-with-docs, that is the same thing.

2

Get grilled

Pick something you actually want, and keep it to one sitting: “a small tool that reads our incident CSV export and produces a weekly summary in Markdown.”

/grill-with-docs

Then describe what you want in a sentence or two. It will interview you in rounds, several numbered questions at a time, each with a recommended answer. It will not start building.

Answer honestly, including “I don't know, you pick”. Every question you answer now is a correction you do not have to make later, when you are not in the room.

💡 The bit that surprises everyone. This is the phase that feels slow and looks like it is not producing anything. It is the phase doing the real work. Half the questions are ones you had not thought about.

3

Turn the interview into a spec

When the questions run out:

/to-spec

You get a written specification. Read it properly. It is the last place where a misunderstanding costs you a sentence instead of a rebuild.

Wrong? Say so in plain English and have it revised. Cheap now.

4

Break it into small tickets

/to-tickets

The spec becomes an ordered list of tickets, each a vertical slice, with the dependencies between them made explicit, so you can see which ones block which.

Look at how small they are. Your instinct will say this is too granular. That instinct is calibrated for humans, who carry context between tasks for free. An agent does not.

🗣️ Try asking: “Why is ticket 3 separate from ticket 4?” The answer is usually about keeping each one inside a single fresh context, which is exactly the point.
5

Walk away

/implement

Now leave it alone. It works through the tickets, writing tests as it goes, running them and any type check the project has, committing to the current branch, and reviewing its own work at the end.

Go and get a coffee. The point of the exercise is to not watch. If you sit there supervising, you have rebuilt the thing this replaces.

📌 It commits as it goes, to whatever branch you are currently on. If that matters to you, make a branch before you start, or ask the agent to make one.

6

Review what came back

/code-review

It asks what to compare against: a commit, a branch, or main. If you started from a clean branch, say the commit you began at, or the branch you branched from.

Then it reviews along two independent axes at the same time: does the code meet a general quality baseline, and does it do what the spec said. Both run as separate reviewers, so neither one's opinion contaminates the other's.

Code can be well written and answer the wrong question, and a review that only looks at style will sign it off.

🔐 And add the one from today. Follow up with the built-in review. You just generated code you did not read. Lesson 08's habit applies here.

/security-review

Now leave the agent:

/exit

Pressing Ctrl + C twice does the same thing. You are back at your normal terminal prompt.

Key takeaways

  • The expensive resource is your attention, not the agent's time. Design the work so your attention is needed in one block, at the front.
  • Small tickets are a context strategy, not project-management ceremony. One slice, one clean window, no inherited confusion.
  • The interview feels unproductive and is the highest-leverage part. Every question you answer there is a correction you do not have to make while you are out of the room.
  • No feedback loop, no AFK. Unattended work is only safe where tests, types and a review pass can check it, and where the controls hold without you watching.
