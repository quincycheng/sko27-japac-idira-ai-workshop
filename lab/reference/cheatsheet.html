Adding an MCP server through the Idira Identity Broker — run this outside the agent, all on one line:

claude mcp add --transport http --scope user idira-broker <GATEWAY-URL> --client-id <CLIENT-ID> --client-secret

--client-secret takes no value — it prompts, so the secret stays out of your shell history. Then /mcp inside the agent to authenticate as yourself. 🙋

4 · idsec — the Idira CLI

idsec version                                     # is it installed?
idsec login                                       # log in (prompts for password/MFA)
idsec login --force                               # log in again before the token expires
idsec profiles list                               # which profiles exist
idsec sca cloud-access list-targets --csp aws     # what may I elevate into?
idsec sca cloud-access elevate --csp aws \
  --workspace-id <aws-account-id> \
  --roleIds <role-arn>                            # ask for access

⚠️ Two rules. Don't run idsec configure again after the prework — it overwrites your settings. And take account IDs and role ARNs from list-targets output rather than typing them from memory.

Flags change between releases. When in doubt: idsec sca cloud-access elevate --help. Logs for anything that fails opaquely: ~/.idsec/logs/idsec-cli.log.

🖥️ And one layer lower: on a managed endpoint, Idira EPM decides whether a CLI like this is allowed to run at all, and by whom — application control plus an approval flow, audited. EPM = which tool may run here. Secure Cloud Access = what access it can obtain. Secrets Manager = what happens to the secrets you cannot eliminate.

7 · The Identity Broker, in six lines 🛡️

ThingWhere / what
Gateway URL shapehttps://<region>.data.aigw.cyberark.cloud/mcp/<server-name>
Client ID + SecretIssued when an admin registers an AI agent
Access policiesManage > Policies > AI agents access → Create policy
The four policy stepsGeneral details → MCP servers and tools → AI agents → Users and roles
Role needed to write oneSecure AI Admin
Kill switchSet the MCP server to Disabled. Instant, for every agent.

Deny-by-default: a request is allowed only where a policy matches both the principal (user/role and agent) and the resource (tool on a server). Both the agent and the server must be enabled. Tools are discovered the first time an agent connects — before that, the count reads Not discovered yet. Every tool run is audited, success or failure. 📋

9 · Installing the skills

Run from inside sandbox-app:

mkdir -p .claude/skills
cp -R ../skills/idsec ../skills/zsp-aws .claude/skills/
New-Item -ItemType Directory -Force .claude\skills | Out-Null
Copy-Item -Recurse -Force ..\skills\idsec, ..\skills\zsp-aws .claude\skills\

To have them in every project on your machine, copy them to ~/.claude/skills/$HOME\.claude\skills\ instead.

The one idea 🧭

When you find a stored secret, ask “does this need to exist at all?” before you ask “where should we keep it?”

If the platform can issue access on demand — as AWS can, through Idira Secure Cloud Access — eliminate it. ✂️ If it cannot, onboard it into Idira Secrets Manager. 🔒 Both are good answers. Only one of them removes the risk permanently — and in a client's production environment, everything you cannot eliminate belongs in the vault, never in a config file or a long-lived environment variable.
