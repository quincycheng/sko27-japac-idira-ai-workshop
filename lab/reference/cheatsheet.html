2 · Where the credentials come from

One login and one command. They expire, so you will do this more than once.

idsec login

Then ask for the credentials. One line, into the terminal you are working in:

eval "$(idsec exec sca cloud-access elevate --csp aws --workspace-id 409556437035 --roleIds arn:aws:iam::409556437035:role/CW-SCA-AdminAccess --raw | jq -r '.response.results[0].accessCredentials | fromjson | "export AWS_ACCESS_KEY_ID=\(.aws_access_key)\nexport AWS_SECRET_ACCESS_KEY=\(.aws_secret_access_key)\nexport AWS_SESSION_TOKEN=\(.aws_session_token)"')"
idsec exec sca cloud-access elevate --csp aws --workspace-id 409556437035 --roleIds arn:aws:iam::409556437035:role/CW-SCA-AdminAccess --raw | jq -r '.response.results[0].accessCredentials | fromjson | "$env:AWS_ACCESS_KEY_ID=\"\(.aws_access_key)\"\n$env:AWS_SECRET_ACCESS_KEY=\"\(.aws_secret_access_key)\"\n$env:AWS_SESSION_TOKEN=\"\(.aws_session_token)\""' | Invoke-Expression

Nothing prints. That is success. To see which accounts and roles you may ask for:

idsec exec sca cloud-access list-targets --csp aws

To prove it worked:

python -c "import boto3; print(boto3.client('sts').get_caller_identity()['Arn'])"

4 · idsec, the Idira CLI

Log in, see what you may elevate into, then ask for it. Take account IDs from the output, never from memory.

idsec version                                     # is it installed?
idsec login                                       # log in (prompts for password/MFA)
idsec login --force                               # log in again before the token expires
idsec profiles list                               # which profiles exist
idsec configure --profile-name <other-tenant>      # park another tenant under its own name
idsec exec sca cloud-access list-targets --csp aws # what may I elevate into?
idsec exec sca cloud-access elevate --csp aws \
  --workspace-id <aws-account-id> \
  --roleIds <role-arn> --raw                      # ask for access

⚠️ Three rules. CYBRWorld belongs on the default profile, the one called idsec. Every command here leaves --profile-name off, so every command uses that one. Don't run idsec configure again after setup, because it overwrites the default profile. Take account IDs and role ARNs from list-targets output rather than typing them from memory.

Flags change between releases. When in doubt: idsec exec sca cloud-access elevate --help. Logs for anything that fails opaquely: ~/.idsec/logs/idsec-cli.log. Full documentation: cyberark.github.io/idsec-cli-golang.

Certificate error on a corporate network? Try --trusted-cert <path.pem> first, then --proxy-address <url>. --disable-cert-verification exists and is a last resort: it turns verification off, so use it today and never at a client.

And one layer lower: on a managed endpoint, Idira EPM decides whether a CLI like this is allowed to run at all, and by whom. That is application control plus an approval flow, audited. EPM = which tool may run here. Secure Cloud Access = what access it can obtain. Secrets Manager = what happens to the secrets you cannot eliminate.

🔓 One thing Part 1 does that you must never copy. Every HTTPS connection in ai-harness-app is made with certificate verification switched off. There is one reason: a corporate TLS-inspecting proxy would otherwise end your session at Lesson 01 with an error nobody in the room can fix, and we would spend the hour on trust stores instead of on agents.

It is the wrong choice everywhere else, and worth being able to say why: unverified TLS means anything on the path can read and rewrite what you send the model and what comes back. From Lesson 04 on, that includes the tool calls the agent decides to make. An attacker who can rewrite a tool result can steer the agent. That is the same argument Lesson 05 makes about prompts, one layer down.

What you do at a client instead: keep verification on, and point the trust store at the proxy's own root CA: export AWS_CA_BUNDLE=/path/to/corp-root.pem$env:AWS_CA_BUNDLE="C:\path\to\corp-root.pem". It is one line, one place: config.py, the note at the top. Go and read it. It names itself as a shortcut, which is the least a shortcut owes you.

The one idea

If you remember one sentence from the whole afternoon, make it this one.

When you find a stored secret, ask “does this need to exist at all?” before you ask “where should we keep it?”

If the platform can issue access on demand, as AWS can through Idira Secure Cloud Access, eliminate it. If it cannot, onboard it into Idira Secrets Manager. Both are good answers. Only one of them removes the risk permanently. In a client's production environment, everything you cannot eliminate belongs in the vault, never in a config file or a long-lived environment variable.
