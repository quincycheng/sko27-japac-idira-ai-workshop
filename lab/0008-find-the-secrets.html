🧪 Everything in this app is fake. Every key, token and password you are about to find is a public example value. None of them open anything, anywhere. You can read them out loud.

Your Tasks

Do not open a file by hand until the agent has told you which one to look at.

1

Run it and watch it fail

Still in the chat? Press Esc, then leave the agent:

/exit

Now, in your terminal:

python summarize.py

You will get an error. Read it. It is the first clue.

Notice what it does not say. It does not say “no credentials found”. It says the credentials it has were rejected. So the app has credentials. It just has bad ones. Where are they?

2

Ask the agent, don't go hunting

Start the agent again:

claude

The bottom line should say auto. If it does not, press Shift + Tab until it does.

Then paste this in:

Run "python summarize.py". Explain why it fails, in plain English, to someone who is not a developer. Do not fix anything yet.

In auto mode it runs the command without asking you. Read its answer.

It should point you at config/settings.py. Have a look at that file yourself, and read the comment above the credentials.

😬 That comment. # TODO: move these somewhere safer before we ship this. Whoever wrote this knew. They were not careless, they were busy. This is what almost every real finding looks like.

3

Ask for a proper security review

Now stop looking at the one file you know about, and ask about all of them:

Review every file in this project for hardcoded secrets and credentials. For each one, tell me: which file, what kind of secret it is, and what an attacker could do with it. Make a table. Change nothing.

While it works, notice what you did not have to do: you did not know the file names, you did not know Python, and you did not know what a Slack webhook looks like.

You should get a table with one row per secret. Claude Code can also do this the short way, with a built-in review. That is the optional step at the end of this lesson.

Ask the question that matters

Still in the agent, paste this:

Of the secrets you found, which ones does this app truly need to store, and which ones could be replaced by asking for access at the moment it is needed? Explain the difference.

There are two completely different fixes hiding in that list, and most people only know about one of them.

Behind that one word is a long security prompt. Compare its findings with your own table. Did it catch anything you missed? Did you catch anything it missed?

On Monday, the natural home for this is every pull request, where it reviews exactly what is new.

Onboard vs Eliminate?

There are two honest answers to a stored credential, and they are not interchangeable. Read the last row first.

Onboard itEliminate it
What you do Move the secret into a vault. The app fetches it when it starts. Delete the secret. The app asks the platform for access when it runs.
Secret still exists? Yes, but somewhere much safer, with rotation and an audit trail. No. There is nothing left to steal, leak, or rotate.
Good for GitHub tokens, Slack webhooks, database passwords, and anything with no other way in. Cloud access, where the platform can mint short-lived credentials on demand.
The Idira answer Idira Secrets Manager. The three remaining secrets belong in it: vaulted, rotated, audited, and fetched by the app at run time. Idira Secure Cloud Access, which is what you use in Lesson 09.
Today Named, not done. Vaulting is a session of its own. Lessons 08 and 09.

🎤 Say both halves to a client. “Eliminate what you can, vault the rest.” You will leave today with one of the four secrets gone and three still sitting in a config file, on purpose. Those three are exactly the case for Idira Secrets Manager. Being able to say which fix applies to which secret, and why, is the whole skill.

💡 And about the AI. Ask an agent to “write a script that calls AWS” without saying anything about credentials, and it will often put them straight into the file. That is what most of the code it learned from does. It is getting better, and often reaches for an environment variable instead. But frequently is a bad number when you are shipping sixty times a week. Speed makes review matter more, not less.

Knowledge Check

Pick an answer to see why it is right or wrong.

Which of the four secrets can be made to stop existing altogether?

No. Slack does not hand out temporary webhooks on demand. That token has to be stored somewhere safe, which means a vault. Try again.

✅ Correct. AWS can mint credentials that expire, and Idira can decide who is allowed to ask. So the app never needs a key of its own. That is Lesson 09.

Being inside a URL makes it easier to leak, not easier to remove. That password still needs to exist somewhere. Try again.

Your scanner flags this key on Monday. Rotating it is which kind of fix?

The old key does stop working. But the file still contains a long-lived key tomorrow. You have reset the clock, not stopped it. Try again.

How the key was generated is not what leaked it. The file it lives in is what leaked it. Try again.

✅ Correct. Rotation buys time. It does not change the design. Read sample-incident.txt for what happens when a team rotates for fourteen builds in a row and never asks why the key is there.

🗣️ Ask your agent: “Read sample-incident.txt and tell me whether this app could cause the same incident.” It is a fictional report, but it is the report you write when nobody does Lessons 08 and 09.

Key takeaways

  • Finding secrets is the easy half. An agent read four credentials out of a codebase you had never opened, in about a minute. So would anybody else's agent.
  • Whoever wrote this knew. # TODO: move these somewhere safer is what almost every real finding looks like. They were busy, not careless.
  • Rotation resets the clock; it does not change the design. The new key goes into the same file. Ask why the file needs a key at all.
  • Eliminate what you can, vault the rest, and say the number out loud. One of four goes away today. Three stay, correctly identified as needing Idira Secrets Manager.
