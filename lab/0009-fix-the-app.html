The satisfying part. You are going to make the app work better by taking code out of it — and one of the four secrets will simply stop existing.

Before you start your terminal must still have the elevated credentials from Lesson 08. Quick check — this should print a role name, not an error:

python -c "import boto3; print(boto3.client('sts').get_caller_identity()['Arn'])"

What we are about to change

🔗 Notice the two import lines. They are easy to forget and they matter: a file that still asks for a constant you deleted stops working immediately (ImportError: cannot import name 'AWS_ACCESS_KEY_ID'). Deleting a secret means deleting everything that reaches for it — which is exactly the kind of thing you check when you review an agent's work. 👀

That is the whole fix. When you do not pass credentials, the AWS library looks for them in your environment — which is where your temporary, expiring, audited credentials already are.

2

You should get three bullet points about the incident, then the single most urgent action — written by Claude, running on Bedrock. 🎉

💥 ImportError: cannot import name 'AWS_ACCESS_KEY_ID'? The agent deleted the credentials but left the import that asks for them. Go back into the agent and say: “summarize.py still imports the constants you deleted — remove them from the import and run the app to prove it works.” This is the most common way this lesson goes wrong. 🔗

✅ Stop and appreciate this. The app just authenticated to AWS and there is no credential anywhere in it. Search the whole project if you like — there is nothing to find, because there is nothing there.

3

Prove the key is gone

Don't take our word for it. Look for it:

grep -rI --exclude-dir=__pycache__ "AKIA" . ; echo "--- nothing above means nothing found ---"
Get-ChildItem -Recurse -Include *.py, *.json, *.txt | Select-String -Pattern "AKIA"

No output means no match. 🎯

🧟 Why we skip __pycache__ — and why you should care. Python keeps a compiled copy of every file it imports in a __pycache__ folder, and that copy still contains the old text of the secret until Python rebuilds it. Deleting a credential from source does not reach into caches, build artefacts, container layers or git history. 🕳️

So in a real engagement there is one more step after this one: delete the key at the source — in AWS IAM — now that nothing needs it. That is what makes every stale copy worthless, in every cache, image and old commit you will never find. Removing it from the code is what makes deleting it safe; deleting it at the source is what makes you finished. ✅

🧠 The important distinction. You did not hide the key. You did not move it. You did not rotate it. You removed the need for it. Nothing has to be stored, watched, rotated or revoked — because nothing exists. That is elimination, and it is the strongest fix available.

4

Now find what you did not fix

Back in the agent:

Review this project for hardcoded secrets again. Tell me which ones are
gone, which ones remain, and for each remaining one, why zero standing
privileges cannot solve it.

Three secrets remain: 🐙 GitHub, 💬 Slack, 🗄️ the database. Ask the agent to explain why — it will tell you that none of those systems can mint short-lived credentials on demand, so the secret has to exist somewhere.

Somewhere is a vault. That is Idira Secrets Manager, that is the onboard fix from Lesson 07, and that is a different session. Today you learned to spot the difference — which is genuinely the harder skill. 🧭

🏢 Before you demo this to a client, read this bit. What you just did — deleting the constants and letting the app pick up short-lived credentials from the environment — is the right answer for the AWS key, and it is the right answer in production too.

But it is not a general answer to secrets, and a client will test you on that. In a real production environment:

  • ✂️ Eliminate where the platform allows it. Cloud access, via Idira Secure Cloud Access. No stored credential at all.
  • 🔒 Everything else goes into Idira Secrets Manager — the GitHub token, the Slack webhook, the database password. Vaulted, rotated on a schedule, access audited, and retrieved by the application at run time rather than living in integrations.json.
  • 🚫 Never an environment variable full of long-lived secrets as the destination. That is the same secret in a slightly less obvious place — it still leaks through process listings, crash dumps, CI logs and printenv.

Short-lived environment variables from a zero-standing-privileges elevation are fine, because they expire on their own. Long-lived ones are a config file wearing a disguise. 🎭
