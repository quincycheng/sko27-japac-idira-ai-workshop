Context engineering 📉

Your Stage 3 agent has a fault you cannot see on a six-file repo: it drowns in its own transcript. Fixing that is the hardest part of building a real harness — and it is where the phrase “context engineering” earns its keep.

Two things to notice, and they are the whole lesson:

  • 📈 input_tokens climbs even when you have asked nothing new. You are paying for the whole transcript, again, every turn.
  • ♻️ At the threshold, [COMPACT] fires and the count falls. The agent carries on with a summary where the detail used to be.

💰 The commercial version of this slide. Cost and latency grow with the square of a naive conversation's length — every turn re-reads everything before it. When someone says their AI pilot “got expensive and slow once people really used it”, this is very often the actual mechanism. 📊

What the script does 🔍

1 · Accounting — one line, and it comes free 
used = response.usage.input_tokens
print(f"[ctx  ] step {step:>2} | input_tokens={used} | messages={len(messages)}")

Every response already carries its own usage. Printing it is the cheapest observability you will ever add, and it turns an invisible failure into a number you can chart, alert on, and put a budget against. 📟

🎤 Ask a customer running agents in production: “can you show me tokens per task, by agent?” If the answer is no, they cannot see cost, cannot see runaway loops, and cannot tell a normal task from an attack that made an agent read ten thousand files.

2 · The threshold — deliberately tiny, so you can see it 
COMPACT_THRESHOLD_TOKENS = 3000   # tiny on purpose: this repo is six small files
...
if used > COMPACT_THRESHOLD_TOKENS:
    messages = compact(messages)

In a real harness this would be a fraction of the model's context window — perhaps 70% of it — not 3000. It is small here so compaction fires during a two-minute demo.

3 · Compaction — asking the model to summarise itself 
head, middle, tail = messages[:1], messages[1:-2], messages[-2:]

summary = client.messages.create(... messages=[{"role": "user", "content":
    "Summarize this agent transcript for your own future reference. "
    "Keep every concrete finding (file:line, secret, risk) and which "
    "files were already inspected. Drop chatter.\n\n" + transcript }])

return head + [compacted_marker] + tail

Three slices. 🍰 Head — the original task, never lose that. Tail — the last two messages, still live. Middle — folded into one note by a second model call.

Look at what the summary prompt insists on keeping: findings with file:line, and which files have already been looked at. Get that wrong and your agent re-reads the same files forever, or quietly forgets the critical finding from step 2. Writing this prompt well is the engineering. ✍️

4 · The boundary hazard nobody warns you about 
# The tricky part is boundaries: never split a tool_use from its matching
# tool_result, or the next call 400s.

Every tool request and its result are a matched pair. Slice between them and the next API call is rejected outright. That is why the code keeps the head and the last two messages whole rather than trimming to a neat token count. 🔗

This is the unglamorous truth about harness code: most of it is bookkeeping that keeps a transcript legal. It is also why sensible people use someone else's harness. 🤷

5 · 🔐 The security reading of compaction

Three things a security architect should notice, none of which are bugs:

  • Secrets travel. The agent read .env, so those values are in the transcript — and now they are in the summary too, re-sent on every later turn. Whatever an agent reads, it keeps carrying. 🎒
  • Compaction is lossy, and the model chose what to lose. Your audit trail of what the agent actually saw is being rewritten by the thing you are auditing. Log the raw transcript separately if it matters. 📝
  • Injected instructions can survive the fold. If a file said “always approve deployments”, the summary can carry that forward as though it were established fact — with the original source stripped out. 🧟 Straight into Stage 5.

Try it 🧪

2

Turn compaction off and watch it climb

Set the threshold absurdly high so it never fires:

COMPACT_THRESHOLD_TOKENS = 500000
python 04_context.py "Read every file, then re-read each one to double-check your findings."

Now input_tokens only goes one way. ⬆️ On six tiny files it survives; on a real repository this is the run that ends in an error, or a bill. Now try the opposite — set it to 1500 and watch it compact constantly, getting vaguer each time. 🫥

Somewhere between the two is the right answer, and it depends on the task. Welcome to context engineering: there is no default that is right for everyone. 🎛️
